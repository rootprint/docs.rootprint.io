---
title: 'Trace explorer'
description: 'Filter spans across every trace by service, operation, duration, status, and query, then open the trace behind any span.'
---

The **Traces** page (at `/traces`) searches the span store directly. Filter spans by service, operation, duration, status, or a query, read latency and error rate for what matches, and open the trace behind any span.

It reads the same OTLP spans as the trace waterfall, so it stays empty until spans are arriving. See [Send traces](/traces/send).

## Filters

The toolbar filters every chart and table on the page.

| Filter           | Matches                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------ |
| **Service**      | One service, by `service_name`. The picker lists up to 100 services seen in the range.                       |
| **Search spans** | A query in [Quickwit query syntax](/search/query-language) over span fields.                                 |
| **Duration**     | A preset band from **< 10 ms** to **> 10 s**, or **Custom…** with **Min ms** and **Below ms**. The upper bound is exclusive. |
| **Error** / **OK** | Spans whose status is `error`, or every other span. Click the active button again to clear it.             |
| **Root only**    | Each trace's root span, one per trace.                                                                       |
| Time range       | Up to 30 days.                                                                                               |

**Root only** with **Error** lists traces whose root span failed. Errors deeper in a trace don't match.

Picking an operation adds an operation filter, shown as a chip under the toolbar. Click the chip's **×** to clear it.

Queries run against the fields of the span store, for example:

```text
# HTTP server errors
span_attributes.http.response.status_code:[500 TO 599]

# PostgreSQL calls from one namespace
span_attributes.db.system:postgresql AND resource_attributes.k8s.namespace.name:production
```

A query Quickwit can't parse, or one with unbalanced parentheses or quotes, is reported under the toolbar. The page keeps the last good results on screen until you fix it.

## Charts

Three charts cover every span the filters match:

- **Latency over time**: p50, p95, and p99 span duration.
- **Error rate**: error spans as a share of matching spans.
- **Requests**: matching spans per interval.

Every matching span counts, whatever its kind, so one request crossing four services counts four times. Turn on **Root only** to count one span per trace. [Service health](/traces/services#what-counts-as-a-request) counts differently: only entry spans are requests there.

Durations are stored in whole milliseconds, so percentiles below 1 ms read `<1 ms`.

Hovering one chart moves the readout on all three. Drag across any chart to narrow the time range to that window.

## Operations

The **Operations** tab groups matching spans by span name, up to the 200 names with the most spans. Each row shows:

- the services that emit it, up to 10
- span count, with a sparkline and the rate per minute
- error rate and error count
- p95 duration

Click a column header to sort. The default is most spans first.

Click an operation to filter the page to it and switch to **Spans**. If only one service emits it, the service filter is set too.

Operation names here are raw span names. Service health names operations from `http.route` and similar attributes instead (see [How Rootprint names an operation](/traces/services#how-rootprint-names-an-operation)), and its links into the explorer carry a query that matches the same spans.

## Spans

The **Spans** tab lists matching spans, newest first, 50 at a time behind **Load more**. The figure above the table is the total number of matches.

Each row shows the start time, service, operation, duration, and status, with the HTTP status code when the span has one. The last column holds the start of the trace ID; click it to copy the full ID.

Sort by **Time** or **Duration**. Click a row to open its trace with that span selected. See [Read a trace](/traces/explore).

## Open a trace by ID

Paste a trace ID into **Search spans** and press Enter to open that trace. If the span store has no spans for it, you return to the explorer with the ID run as a text search. Wrap the ID in quotes to search for it as text from the start.

## Links and URL state

Every filter, the time range, the active tab, and the span sort are part of the URL, so you can bookmark or share a filtered view.

[Service health](/traces/services) links here too:

- **View traces** on the catalog opens the explorer over the same time range. On a service's page, it also sets the service.
- The traces icon on a service, operation, or dependency row opens it filtered to that row.
- **Open in Traces** on the **Errors** tab opens it with **Error** on and the tab's filters applied.

## Limits

| Limit                   | Behavior                                                                                         |
| ----------------------- | ------------------------------------------------------------------------------------------------ |
| 30 days per range       | A wider range is rejected with `400`.                                                            |
| 2,000 buckets           | An `interval` that would produce more buckets for the range is rejected with `400`. The UI picks the interval for you. |
| 200 operations          | The span names with the most spans. Past that, the tab says it is showing the top 200.           |
| 100 services            | The service picker lists up to 100.                                                              |
| 50 spans a page         | `limit` accepts up to `100`; `offset` stops at `10,000`, so the list ends there.                  |
| 2,000-character query   | A longer query is rejected with `400`.                                                           |

## Access and auditing

The explorer needs `logs: read`: a session cookie or a query API key. It isn't admin-only or scoped per index, so any actor that can read logs can search spans.

Each request is recorded in the search audit like any other search and counts against the read rate limit. See [Rate limiting](/configuration/environment-variables#rate-limiting).

A missing span store is not an error. If `TRACE_INDEX_ID` points at an index that does not exist, the explorer shows no spans.
