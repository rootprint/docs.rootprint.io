The **Services** page (at `/services`) reads the spans in your span store as request-level metrics: request volume, error rate, and latency per service, the operations taking the most time, each service's downstream calls, and the individual spans that failed.

Nothing extra is ingested for it. The page reads the same OTLP spans as the trace waterfall — see [Send traces](/traces/send) — so it stays empty until spans are arriving.

It has two levels: a catalog of every service, and a page per service at `/services/<name>`. Old `/monitoring` links redirect here, and `/services?service=<name>` redirects to that service's page.

## The summary strip

The summary strip is the same on every tab, and covers the current service and time range:

| Figure          | Meaning                                                                                    |
| --------------- | ------------------------------------------------------------------------------------------ |
| **Error spans** | Spans with an `error` status, across every span kind, including outbound calls.          |
| **Requests**    | Entry spans in the range: server, consumer, or root spans (see [What counts as a request](#what-counts-as-a-request)). |
| **Throughput**  | Those requests per minute.                                                                 |
| **Error rate**  | Failing requests as a share of requests.                                                   |
| **p95 latency** | The 95th-percentile latency of the selected service's requests. With no service selected the figure reads **Slowest p95**: the highest p95 of any service, with that service named beside it. |

A service can serve every request successfully while its outbound calls fail, so a non-zero **Error spans** count next to a `0%` **Error rate** is a valid combination.

## The catalog

`/services` shows the summary strip, three charts (p95 latency per service, request rate, error rate) and a table of every service with requests, error rate, p50 and p95. The table sorts by error rate, worst first; click a column to sort by it. Click a service to open its page.

## A service's page

Every service has the same tabs:

| Tab                      | Contents                                                                                                   |
| ------------------------ | ---------------------------------------------------------------------------------------------------------- |
| **Overview**             | Request rate, error rate, and p50/p95/average request latency.                                             |
| **Operations**           | The service's operations ranked by the total time they account for, with request count, error rate, p50, and p95. |
| **Dependencies**         | Outbound client and producer spans the service emits, ranked by total time.                               |
| **Errors**               | Individual failing spans, newest first. The tab carries the error-span count and turns red when non-zero. |

Each row in **Operations** and **Dependencies** links to the [trace explorer](/traces/search), filtered to that row. **View traces** in the toolbar opens the explorer filtered to the service, and **Open in Traces** on the **Errors** tab carries its filters over.

All charts share one cursor: hovering any of them moves the readout on all. Dragging across any chart narrows the whole page to that window.

## What counts as a request

A request is an **entry span**: a server span (`span_kind:2`, an inbound call), a consumer span (`span_kind:5`, a consumed message), or a root span (a trace the service starts itself, such as a scheduled job). Client, producer, and internal spans with a parent are not requests, so a request crossing three services counts once in each of them. A request is an error when its span status is `error`.

The **Errors** tab is the exception: it lists failing spans of every kind.

## How Rootprint names an operation

An operation name comes from the first of these that the span carries:

1. `http.route` — the templated route (`/users/:id`)
2. `url.path`
3. `http.target`
4. `url.full`
5. the span name

Consumer and root spans usually carry none of the HTTP attributes, so they fall through to the span name.

Rows built from anything other than `http.route` or a path are marked, because a raw URL yields one operation per distinct URL: `/users/1` and `/users/2` become two rows instead of one. If the table reads as a long tail of near-duplicates, the fix is in the instrumentation — enable HTTP route recording in the SDK or framework instrumentation that produces those spans.

## Downstream calls

The **Dependencies** tab groups a service's outbound spans — client (`span_kind:3`) and producer (`span_kind:4`) — by span name, and ranks them by total time, with call count, p50, and p95. Under each call name it lists up to three peers, read from `server.address`, so an HTTP client span shows which hosts it called.

## Failing spans

The **Errors** tab lists error spans newest first, one row per span: time, service, kind, operation, message, HTTP status, and duration. A row opens its trace in a new tab with that span preselected in the waterfall.

The message is the span's own status message, falling back to `exception.message` (then `exception.type`) from the first exception event on the span, truncated at 300 characters. HTTP status is read from `http.response.status_code`, or `http.status_code` from older SDKs; a span carrying neither shows `—`.

Three filters narrow the list, and each one is part of the URL:

- **Kind** — server, client, producer, consumer, or internal.
- **HTTP** — `4xx`, `5xx`, or spans with no HTTP status at all.
- **Top operations** — chips for the 20 operations with the most errors in the range. Click one to scope the list to it.

The list loads 50 spans at a time behind **Load more**.

## Limits

| Limit                   | Behavior                                                                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------- |
| 30 days per range       | A wider range is rejected with `400`. Applies to both service health endpoints.               |
| 2,000 buckets           | An interval that would produce more buckets for the range is rejected with `400`. The UI picks the interval for you and stays inside this. |
| 10 services charted     | The p95-by-service comparison charts the 10 most active services.                              |
| 100 services listed     | Past that, the page says it is showing the most active services only.                          |
| 30 operation rows       | The UI requests 30 and trims to the row count locally; `endpointLimit` accepts `0` to `100`, and `0` skips operations. Operations are only returned with `service`. |
| 20 dependencies         | The 20 downstream calls with the most total time, with up to 3 peers each.                     |
| 20 operation chips      | The 20 operations with the most errors in the range.                                           |
| 50 failing spans a page | `limit` accepts up to `100`; `offset` stops at `5,000`, so the list ends there.                |

## Access and auditing

Reading service health or failing spans needs `logs: read` — a session cookie or a query API key. Neither is admin-only, and neither is scoped per index: any actor that can read logs can read them.

Each request is recorded in the search audit like any other search, and both count against the read rate limit. See [Rate limiting](/configuration/environment-variables#rate-limiting).

<Warning>
	A missing span store is not an error. If `TRACE_INDEX_ID` points at an index that does not
	exist, the page reports that trace telemetry is unavailable rather than failing. See
	[Environment variables](/configuration/environment-variables).
</Warning>
