title: 'Service health'
description: 'Read request rate, error rate, latency, downstream calls, and failing spans from the spans you already send.'
---

The **Services** page (at `/services`) turns the spans you already send into request rate, error rate, and latency per service, plus each service's operations, downstream calls, and failing spans. It stays empty until spans are arriving. See [Send traces](/traces/send), and check `TRACE_INDEX_ID` in [Environment variables](/configuration/environment-variables#optional) if spans should be there.

It has a catalog of every service and a page per service at `/services/<name>`.

## The summary strip

The summary strip is the same on every tab, and covers the current service and time range:

| Figure          | Meaning                                                                                    |
| --------------- | ------------------------------------------------------------------------------------------ |
| **Error spans** | Spans with an `error` status, across every span kind, including outbound calls.          |
| **Requests**    | Entry spans in the range (see [What counts as a request](#what-counts-as-a-request)).      |
| **Throughput**  | Those requests per minute.                                                                 |
| **Error rate**  | Failing requests as a share of requests.                                                   |
| **p95 latency** | The 95th-percentile request latency. With no service selected, **Slowest p95** shows the highest p95 of any service and names it. |

A service can serve every request successfully while its outbound calls fail, so a non-zero **Error spans** count next to a `0%` **Error rate** is a valid combination.

## The catalog

`/services` shows the summary strip, three charts (p95 latency per service, request rate, error rate) and a table of every service with requests, error rate, p50 and p95. The table sorts by error rate, worst first. Click a service to open its page.

## A service's page

Every service has the same tabs:

| Tab              | Contents                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| **Overview**     | Request rate, error rate, and p50/p95/average request latency.                                             |
| **Operations**   | The service's operations ranked by total time, with request count, error rate, p50, and p95. See [How Rootprint names an operation](#how-rootprint-names-an-operation). |
| **Dependencies** | Outbound calls, ranked by total time. See [Downstream calls](#downstream-calls).                           |
| **Errors**       | Failing spans, newest first. See [Failing spans](#failing-spans).                                          |

Each row in **Operations** and **Dependencies** links to the [trace explorer](/traces/search), filtered to that row. **View traces** in the toolbar opens the explorer over the same time range, filtered to the service on a service's page. **Open in Traces** on the **Errors** tab carries its filters over.

Drag across any chart to narrow the whole page to that window.

## What counts as a request

A request is an **entry span**: a server span (an inbound call), a consumer span (a consumed message), or a root span (a trace the service starts itself, such as a scheduled job). Client, producer, and internal spans with a parent are not requests, so a request crossing three services counts once in each of them. A request is an error when its span status is `error`.

## How Rootprint names an operation

An operation name comes from the first of these that the span carries:

1. `http.route` — the templated route (`/users/:id`)
2. `url.path`
3. `http.target`
4. `url.full`
5. the span name

A row whose name falls back to a bare HTTP method, such as `GET`, is marked **Route unavailable**. A raw path or URL makes one operation per distinct value, so `/users/1` and `/users/2` become two rows. If the table reads as a long tail of near-duplicates, enable HTTP route recording in the SDK or framework instrumentation that produces those spans.

## Downstream calls

The **Dependencies** tab groups a service's client and producer spans by span name, ranked by total time, with call count, p50, and p95. Each call lists up to three peers, read from `server.address`, so an HTTP client span shows which hosts it called.

## Failing spans

The **Errors** tab lists error spans of every kind, newest first: time, service, kind, operation, message, HTTP status, and duration. A row opens its trace in a new tab with that span selected.

The message is the span's status message, or the message of its first exception event. HTTP status is read from `http.response.status_code` or `http.status_code`.

Three filters narrow the list:

- **Kind** — server, client, producer, consumer, or internal.
- **HTTP** — `4xx`, `5xx`, or spans with no HTTP status at all.
- **Top operations** — chips for the 20 operations with the most errors in the range. Click one to scope the list to it.

## Limits

| Limit                   | Behavior                                                                       |
| ----------------------- | ------------------------------------------------------------------------------ |
| 30 days per range       | A wider range is rejected.                                                     |
| 10 services charted     | The p95-by-service comparison charts the 10 most active services.              |
| 100 services listed     | Past that, the page says it is showing the most active services only.          |
| 30 operation rows       | The **Operations** tab shows 10, 20, or 30 rows.                               |
| 20 dependencies         | The 20 downstream calls with the most total time, with up to 3 peers each.     |
| 5,000 failing spans     | The **Errors** list loads 50 at a time and stops at about 5,000.               |
